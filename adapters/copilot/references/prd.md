# PRD Reference

Use this reference when drafting a product requirements document.

## Purpose

A PRD defines what the product should do, who it is for, why it matters, and how success will be judged.

## Recommended Structure

1. Product Overview
2. Problem Statement
3. Goals and Non-Goals
4. Personas
5. Core User Journeys
6. MVP Scope
7. Functional Requirements
8. Non-Functional Requirements
9. Success Metrics
10. Risks and Open Questions

## Writing Rules

- Write for product, design, and engineering readers.
- Keep requirements concrete and testable.
- Separate must-have scope from nice-to-have scope.
- Use tables for fields, scope, and metrics when that improves readability.
- Use Gherkin-style acceptance criteria when the requirement benefits from explicit examples.
- Include open questions instead of silently guessing.

## Section Guidance

- Product Overview: product name, one-line description, platform, language, and technical constraints.
- Problem Statement: the user pain that the product solves.
- Goals and Non-Goals: what this release should achieve and what it intentionally will not cover.
- Personas: 2 to 4 representative users with goals and pain points.
- Core User Journeys: step-by-step flows that show the main product actions.
- MVP Scope: prioritize features clearly, usually with Must Have / Should Have / Could Have / Won't Have.
- Functional Requirements: describe behavior, data fields, and expectations in a way that can be implemented and reviewed.
- Non-Functional Requirements: performance, reliability, security, accessibility, or device constraints.
- Success Metrics: launch targets and product health signals.
- Risks and Open Questions: unresolved dependencies, assumptions, and known tradeoffs.

## Quality Check

- Every major feature should map back to a goal or user journey.
- Every requirement should be traceable to a need.
- Every assumption should be labeled as an assumption.
